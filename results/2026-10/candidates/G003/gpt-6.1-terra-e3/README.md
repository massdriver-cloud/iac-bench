# App Service for containerized APIs

This root deploys a dedicated Linux Premium v3 plan, an HTTPS-only container app, a staging slot, CPU autoscaling, workspace-based Application Insights and App Service diagnostics. Use an existing resource group, globally unique app name and environment-supplied AzureRM credentials (including `ARM_SUBSCRIPTION_ID`). `minimal.tfvars` is an example: replace the resource group and app name with real values before applying. Run `tofu init`, `tofu plan -var-file=minimal.tfvars`, then `tofu apply -var-file=minimal.tfvars`.

## Operations

- By default one instance runs, scaling to three when average CPU exceeds 70% for ten minutes, and back down below 30%. These are not highly available defaults: set `min_instances` to at least 2 for redundancy, or enable `zone_balancing_enabled` with at least 3 instances in a region and SKU supporting zone redundancy. Slots share the plan's capacity. Select a SKU supporting slots, health checks and autoscaling.
- Set `container_port` and an unauthenticated `health_check_path` returning 2xx when ready. App Service removes persistently unhealthy instances where possible; it does not guarantee availability with one worker. Containers need to listen on all interfaces. Storage is ephemeral; use external persistence.
- The default image is pulled from Docker Hub. For private ACR set its HTTPS login server in `container_registry_url` and its resource ID in `acr_resource_id`; the deployment identity needs permission to create AcrPull role assignments. Each slot gets its own system identity. Initial pulls can fail until RBAC propagates. For other private registries provide both registry credentials instead. Credentials and app settings are stored in state: secure the backend and prefer Key Vault references for application secrets. Private registries requiring private network access need additional networking not provided here.
- To roll out, set `staging_container_image` to the candidate and apply, verify the staging URL and health, then swap the staging slot with production using Azure tooling. Immediately update `container_image` to the promoted image and `staging_container_image` to the previous production image before the next apply; otherwise OpenTofu will reconcile the swap back to the declared images. Swap back to roll back and update inputs again. Avoid mutable tags. No automatic swap or smoke test is performed. Staging is public and has the same settings as production; protect sensitive endpoints in the application and do not use production side effects during tests.
- HTTP, container console, application and platform logs plus metrics flow to Log Analytics. The Application Insights connection string is injected, but application traces and request telemetry require appropriate SDK/agent instrumentation in the container. Configure alerting and notification routing separately. Diagnostics and telemetry incur charges, and log retention is configurable.

The app and slot are public, with HTTPS and TLS 1.2 enforced. This module does not create private networking, a custom domain, certificates, access restrictions, backups, alert routing, or a deployment pipeline. Restrict access externally as required. Resource group, globally unique names, region/SKU availability, quotas and necessary registry/network permissions are prerequisites.
