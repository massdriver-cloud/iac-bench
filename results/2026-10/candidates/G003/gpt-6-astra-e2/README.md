# Standard SRE App Service root

A standalone OpenTofu root for **one stateless Linux HTTP container service**. Resources are authored here; there are no remote module calls. Run this directory directly, with a separate state per service/environment.

## Operational contract

| Concern | Decision |
|---|---|
| Capacity | Dedicated Premium v3 Linux plan, P1v3 by default. Three workers across availability zones, autoscale floor 3 / ceiling 6. Region and subscription must support this SKU and zone redundancy. |
| Scaling | Scale out one worker on average CPU >70% **or** memory >80% for 5 minutes; 5-minute cooldown. Scale in one only when CPU <30% **and** memory <60% for 15 minutes; 10-minute cooldown. Azure Monitor owns live worker count, avoiding IaC scale resets. |
| Health | Always On; `/health` by default; 3 failed platform probes before unhealthy handling, 5-minute unhealthy eviction setting, at most 50% excluded. These are Azure health mechanisms, not a guarantee of recovery time. No session affinity. |
| Rollouts | Staging slot on the same plan, manual approval and swap, explicit candidate image. No automatic image updates or auto-swap. Separate slot identities and telemetry. |
| Transport | HTTPS-only, TLS >=1.2 for app and SCM, HTTP/2. FTP and publishing basic authentication disabled. Azure manages the default hostname's certificate. |
| Ingress | Production is public by default. Optional CIDR allowlist. Staging and both SCM endpoints default-deny; `management_cidrs` permits operator/CI egress. Application auth is the product team's responsibility. |
| Egress | Optional existing delegated subnet, route-all and image pulls through that VNet. No VNet, NAT, private DNS, private endpoints or firewall created. |
| Telemetry | All supported platform log categories and metrics to a dedicated Log Analytics workspace, 30-day retention. Separate workspace-backed Application Insights per slot. Short-lived local HTTP logs: 7 days / 35 MB. |
| Alerting | SRE email action group. >5 production HTTP 5xx / 5 minutes; plan CPU or memory >90% / 15 minutes. Public readiness test every 5 minutes from three locations, alert on two failed locations (including TLS checks). Autoscale notifications also go to the SRE mailbox. |

This is a single-region availability design, **not regional disaster recovery**. Staging consumes production plan capacity: do not load-test it without headroom. Zones do not protect regional dependencies. Lowering capacity below three requires explicitly disabling zones; one worker is not highly available. Zone or SKU changes may require replacement; review every plan.

## Start

Prerequisites: OpenTofu >=1.6, Azure credentials in the environment (for example `ARM_SUBSCRIPTION_ID`, `ARM_TENANT_ID`, `ARM_CLIENT_ID` plus workload identity or client-secret credentials). The deployment identity needs resource creation permissions, provider registration permissions or pre-registered providers, and role-assignment permissions at the registry if private ACR is used. Subnet integration requires subnet join permissions. Relevant providers include Microsoft.Web, Microsoft.Insights, Microsoft.OperationalInsights and Microsoft.ManagedIdentity.

```sh
tofu init
tofu fmt -check
tofu validate
tofu plan -var-file=minimal.tfvars -out=service.tfplan
tofu apply service.tfplan
```

`minimal.tfvars` supplies literal values for all required inputs: `name`, `container_image`, and `alert_email_addresses`. Replace its globally unique app name and example mailbox before deployment. Its public demo image serves port 80 at `/`; the `latest` tag is **only a smoke-test convenience**, not a production release strategy. The defaults deliberately incur Premium worker, telemetry ingestion, and standard availability-test charges. No free-tier fallback is performed.

No backend is hardcoded so this root can initialize independently. Before real production use, configure a secured remote backend with locking and tightly restricted access (for example an Azure Storage backend). Local state is not a production operating model. Commit the generated provider lockfile; keep state, saved plans, credentials and secret-bearing tfvars out of version control. The lockfile, if generated by initialization, pins the exact provider selected within the supported AzureRM 4.x range.

## Application and configuration requirements

- Listen on `0.0.0.0:container_port` (default 8080), HTTP behind Azure TLS termination. `WEBSITES_PORT` controls platform routing; configure your application to listen on that port too.
- Implement a cheap, unauthenticated, nonredirecting readiness endpoint returning **200** only when safe to serve traffic. App Service accepts 2xx, but swap warmup and synthetic tests intentionally require 200. Do not redirect based on a custom hostname or require API credentials at this endpoint. It must not expose sensitive data.
- Start within 300 seconds, handle termination gracefully, and keep sessions, uploaded files and durable data outside the container. App Service persistent storage is disabled; container disk is disposable. There is no database, backup or migration automation here.
- Emit structured stdout/stderr logs. Install an Application Insights SDK or Azure Monitor OpenTelemetry exporter and consume `APPLICATIONINSIGHTS_CONNECTION_STRING` for request/dependency/tracing telemetry. Injecting that setting alone does **not** instrument an arbitrary image. Scrub secrets/PII and configure SDK sampling for high-volume workloads; platform logs and ingestion are billable.
- Use a versioned immutable image tag or digest: `container_image = "team/api@sha256:..."`, without the registry hostname. The module never builds images. Set `registry.url` to the HTTPS registry origin.
- For private ACR, set `registry.acr_resource_id`. Both slot-specific user-assigned identities receive only `AcrPull`, scoped to that registry, before app creation. Azure RBAC propagation may still delay initial pulls; inspect startup logs and retry/restart after propagation. ACR must use standard registry RBAC mode: ABAC repository permissions need a different role model and are not supported here. Non-ACR registries must permit anonymous pulls; no registry password input is exposed.
- Application SDKs use each slot's **system-assigned identity** by default. `runtime_principal_ids` exposes these principals for least-privilege grants. Pre-created **user-assigned identities** are used for image pulls and Key Vault references; `identities` exposes those principals. No subscription-wide application grants are created.
- Use `@Microsoft.KeyVault(SecretUri=https://.../secrets/...)` values in `app_settings`, rather than plaintext secrets. Grant the relevant user-assigned identity `Key Vault Secrets User` and provide vault networking separately. These grants are not implicit. Marking inputs sensitive only redacts CLI output: all settings and telemetry connection strings are still stored in state.
- `app_settings` is shared. `staging_app_settings` overrides it for staging (for example a staging database URL). All override **names** are automatically sticky, as are environment/telemetry settings. Add other environment-bound keys to `sticky_app_setting_names`. Platform-owned settings always win over user values. Setting names are not treated as secrets.

The most useful knobs are `capacity`, `sku_name`, `container_port`, `health_check_path`, `staging_container_image`, `management_cidrs`, and `tags`; `variables.tf` describes every input. For strictly IP-allowlisted production APIs, set `ingress_cidrs` and **disable** `enable_public_availability_test`; a precondition prevents knowingly deploying blocked public probes. SRE must then supply an internal synthetic check. Outbound VNet integration does not make inbound traffic private. Use a suitably sized, same-region subnet (at least /26 recommended), delegated to Microsoft.Web/serverFarms, with working DNS, egress and registry/telemetry connectivity. Both slots share the subnet.

## Release and rollback runbook

Use a serialized pipeline; no concurrent applies, swaps or portal config edits. For A -> B:

1. Keep `container_image=A`, set `staging_container_image=B`, and apply a reviewed plan. A direct change to `container_image` restarts production rather than performing a gated rollout.
2. Allow the CI/operator public egress CIDR in `management_cidrs`. Check staging readiness and run smoke tests through `staging_url`; inspect its Application Insights and console logs. A 403 with no allowlist is intentional. ARM container configuration and slot swap commands do not require SCM access. SCM publishing uses Entra authentication, not basic auth.
3. Ensure backward-compatible schema changes and capacity headroom. Slots share a service and plan, so they are not a strong security or performance isolation boundary. Azure applies target sticky settings to the source during swap warmup while identities remain slot-bound. Authorize only the dependency access required for that warmup for the source identities, and ensure startup/readiness does not mutate production data. If this violates isolation policy, use a separate service/plan deployment strategy rather than a slot swap. Never bypass readiness to force promotion.
4. After approval, swap via the Azure control plane:

   ```sh
   RG=$(tofu output -raw resource_group_name)
   APP=$(tofu output -raw app_name)
   az webapp deployment slot swap --resource-group "$RG" --name "$APP" \
     --slot staging --target-slot production
   ```

   Azure warms the candidate using the configured path and requires HTTP 200 before completing the swap. This gate complements, but does not replace, smoke tests or SLO review.
5. Verify production readiness, error rates, dependencies and saturation. **Immediately reconcile desired state:** set `container_image=B`, `staging_container_image=A`; run a fresh normal plan to refresh state and review it, then apply only the expected reconciliation. Preserve nonsticky release-setting values in the correct slots too. Until reconciliation, a normal apply would revert the images! Image/config drift is intentionally not ignored. Do not reuse a pre-swap saved plan.
6. Keep A in staging during the observation window. To roll back, swap again, verify service, then restore inputs to production A / staging B and reconcile. Never assume a swap rolls back a database migration. Keep previous immutable artifacts available for both identities.

If staging is disabled, image changes are direct restarts; there is no slot rollback path. Avoid configuration changes to both slots during a release. No unconditional zero-downtime guarantee is made: initialization behavior, dependencies, long-running connections and platform operations all matter.

## Routine operations

- Verify action-group delivery to a real monitored mailbox after apply. Email is the included integration, not a replacement for an on-call escalation system; route that mailbox appropriately or extend the action group. These baseline thresholds are not service-specific SLO/burn-rate alerts.
- On availability or 5xx alerts: check platform health, readiness and container pull/startup logs, then dependencies and recent swaps. Health probes alone do not prove business correctness. Add critical-journey synthetic checks and service-specific SLO alerts as needed.
- On saturation: compare worker count with the ceiling, staging workload, memory growth and dependency bottlenecks. Raise `capacity.maximum` within quota, or scale the worker size with `sku_name`. Scale-out takes time; load-test and reserve headroom.
- Query the workspace's `AppServiceConsoleLogs`, `AppServiceHTTPLogs` and `AppServicePlatformLogs`, filtering resource ID for production versus staging. Application Insights request/dependency data requires application instrumentation. No hard ingestion cap is imposed on the workspace, to avoid intentionally losing incident telemetry; monitor cost.
- Custom DNS/certificates, WAF/Front Door, application auth, private inbound endpoints, data stores and cross-region failover are intentionally outside this per-service root. The default Azure hostname provides working TLS without external DNS prerequisites.
- `tofu destroy` removes the dedicated service, identities, telemetry resources and their retained data. Treat deletion as a reviewed production change; there is no delete lock or `prevent_destroy` escape hatch hidden in this root.
