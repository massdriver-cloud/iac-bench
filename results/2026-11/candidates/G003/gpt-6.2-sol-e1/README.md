# Linux App Service for containerized APIs

Use one root deployment and one state per service and environment. The module owns a resource group, dedicated Linux plan, production app, and Azure Monitor resources. It optionally adds a staging slot and permissions on an existing Azure Container Registry (ACR). It does not create a registry, network, or action group.

## Get started

1. Supply AzureRM credentials and subscription through the environment (for example, `ARM_SUBSCRIPTION_ID` and federated workload credentials in CI). Ensure `Microsoft.Web`, `Microsoft.Insights`, `Microsoft.OperationalInsights`, and, for ACR pulls, `Microsoft.ManagedIdentity` are already registered. The provider does not register namespaces automatically. Using ACR requires permission to create the role assignment at its scope; VNet integration requires subnet join permission.
2. Copy `minimal.tfvars` to a deployment-specific file, choose a globally unique app name, and set the region and image. The supplied file uses a public demo image. Use an immutable version tag or digest for real releases. The image must listen on `0.0.0.0` at `container.port` (default `8080`), serve HTTP, and be stateless across restarts and scale-out.
3. Run `tofu init` and `tofu plan -var-file=minimal.tfvars`. Review and apply the intended plan. Configure a protected remote backend with locking for team deployments before the first apply; keep a separate state key per deployment. State contains app configuration, so restrict access to it.

## Operating defaults

- **Capacity:** Premium v3 (`P1v3`), two starting/minimum workers and five maximum. Azure Monitor adds one worker when plan CPU averages over 70% for five minutes and removes one when it averages below 30% for 15 minutes, with five- and ten-minute cooldowns respectively. Set `capacity.minimum` and `capacity.maximum` to the same number for fixed capacity. Change bounds through the module, not by editing the live worker count. Slots share the same workers and count toward plan load.
- **Availability:** Two workers protect against a single worker failure but do not guarantee zone isolation. Set `capacity.zone_redundant = true` for zone redundancy on a supported region and App Service stamp; it requires at least two workers. This module does not provide regional failover. Even the demo provisions a billable Premium plan and can incur telemetry charges.
- **Readiness:** `/healthz` by default, with Always On. The endpoint must return `200` without authentication or redirects when the app can serve traffic. The same path gates startup and swap warm-up. App Service health checks mark a worker unhealthy after two failed one-minute probes, subject to platform health check limits.
- **Access and secrets:** Production is public over HTTPS with TLS 1.2 or newer. Implement API authentication in the app or at an upstream gateway. FTP and publishing basic authentication are off. Use Key Vault references rather than putting secrets in tfvars; grant each slot's own system-assigned identity access to only the secrets it needs. The app and slot have separate system-assigned identities; a separate shared identity has only registry pull permission.
- **Container pulls:** `container.registry_url` is the HTTPS login server; `container.image` is the repository and version without the login server. For an existing ACR in classic registry RBAC mode, set `container.acr_id` to grant the pull identity `AcrPull`. ABAC repository permissions are not managed here. Role propagation can delay the first successful pull. `integration_subnet_id` enables outbound integration on an existing same-region subnet delegated to `Microsoft.Web/serverFarms`; when combined with ACR it also routes image pulls through the VNet. Provide working registry DNS and network reachability. VNet integration does not make app ingress private.
- **Telemetry:** Production and staging send HTTP, container console, and platform logs plus metrics to the workspace. Write application logs to stdout/stderr. Both slots get the workspace-backed Application Insights connection string; instrument the image with a supported SDK or Azure Monitor OpenTelemetry distro to send application traces and dependencies. Tag telemetry by environment in the instrumented app to distinguish slots. Set `action_group_ids` to enable a production alert for 10 or more HTTP 5xx responses in five minutes. Logs and APM are not an external availability probe; use your SRE synthetic monitoring for client-side uptime.

## Release with a slot

`staging.example.tfvars` illustrates a versioned private image, zone redundancy, an alert, and a staging allowlist. It contains placeholder resource IDs and is not intended for apply as-is.

1. Enable `staging` and set `staging.image` to the candidate while leaving `container.image` pinned to the production version. Configure staging settings separately and use `sticky_app_setting_names` for settings that must stay with production or staging (for example, environment and Key Vault references). Staging and its SCM endpoint deny external requests unless a CIDR is allowed.
2. Apply, then smoke-test the staging HTTPS URL from an allowed network. Check readiness and telemetry. Trigger the staging-to-production swap from your release pipeline via Azure, not as a standing OpenTofu resource. Ensure the candidate can warm up with the target settings; Azure warms the source before it switches traffic.
3. Verify production. If verification fails, swap back while the previous revision is still in staging. After a successful swap, update the declared production and staging images and any swapped non-sticky settings to match Azure **before** the next apply. Otherwise OpenTofu will restore the pre-swap configuration. Serialize swaps and applies in the release pipeline.

Without staging, a change to `container.image` redeploys production directly; this is not a staged rollout.
