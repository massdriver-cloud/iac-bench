# Regional GKE Standard cluster

This root module creates one regional, VPC-native GKE Standard cluster and an autoscaling, multi-zone node pool. It uses the existing `apps-staging` or `apps-prod` network and `<network>-gke-<region>` subnet in the same project, with secondary ranges `pods` and `services`. It does not create or modify the VPC, subnet, Cloud NAT, or workload IAM permissions.

## Before applying

* Use environment-provided Google credentials with permissions to enable APIs, create GKE clusters, service accounts and project IAM bindings, use the network/subnet, and act as the node service account. Enable Service Usage API beforehand. Billing, resource quotas and GKE availability in the chosen US region are prerequisites. Enabling the required project APIs is managed here; they are deliberately left enabled on destroy.
* Coordinate with the network team. Private nodes have no public IPs: provide Private Google Access on the subnet and outbound Cloud NAT (or equivalent egress) for nodes and Pods, including registry and external endpoints. Permit GKE control-plane/node and health-check traffic and required DNS/Google API access. NAT/firewall resources are intentionally not created because the subnet and egress are shared and network-team managed.
* Reserve a unique non-overlapping RFC1918 /28 for the control plane, including against peered and on-prem networks. Ensure the node subnet and both secondary ranges have enough free addresses for the cluster, per-node Pod CIDRs, autoscaling, temporary default nodes and surge upgrades. Check GKE's secondary-range sharing restrictions and capacity before placing multiple clusters on this subnet.
* Supply administrator source CIDRs for the public Kubernetes API endpoint. Use small trusted VPN or office egress ranges, not the documentation-only address in the example. GKE also permits required internal control-plane access; IP allowlisting is not a replacement for Google IAM and Kubernetes RBAC. The example tfvars is illustrative, not deployable as-is: replace the project, IP ranges and names with real values.
* Keep state in a secured remote backend with locking and restricted access; configure it at initialization. State can contain cluster connection details. Bootstrap project-level access and backend separately.

Run `tofu init`, then `tofu plan -var-file=minimal.tfvars` and `tofu apply -var-file=minimal.tfvars` with your real values. To connect, run `gcloud container clusters get-credentials CLUSTER --region REGION --project PROJECT` from an authorized network, using the GKE gcloud auth plugin and an identity with appropriate IAM and Kubernetes RBAC.

## Operations and security

The regional control plane and node pool span GKE's default regional node zones (normally three). Each zone starts with one non-spot node and can autoscale to `max_nodes_per_zone`; allow additional IPs and quota for one surge node per zone during upgrades. Use multi-replica workloads with topology spread, disruption budgets and appropriate resource requests; a regional cluster alone cannot make an application highly available. GKE repairs nodes and upgrades on the Regular release channel, normally within the Saturday/Sunday 02:00–10:00 UTC maintenance windows; urgent maintenance can occur outside them.

Dataplane V2 enforces Kubernetes NetworkPolicy; teams must actually create policies, including default-deny where appropriate. Shielded nodes use Secure Boot and integrity monitoring. System and workload logs, system metrics and managed Prometheus are enabled; configure alert policies, notification channels, log retention and dashboards according to your operations standards. Logging, metrics and GKE services incur charges. The GKE basic security posture and vulnerability scanning are enabled; review their findings.

Workload Identity Federation is enabled, but grants no application permissions by itself. Create separate Kubernetes service accounts per workload and grant the corresponding workload identity principal only the Pub/Sub, Storage, SQL or other permissions it needs on the relevant resources (or configure IAM service-account impersonation where required). Do not put workload permissions on the node service account or use service-account keys. Cloud SQL connectivity additionally requires an appropriate network path and the Cloud SQL Auth Proxy/connector or another approved connection method. This module does not configure product-team namespaces, RBAC, policies or Google service resources.

Deletion protection is on by default. To intentionally destroy, first set `deletion_protection = false` and apply, then destroy. Destruction removes the cluster, node pool and dedicated node IAM identity, but retains shared APIs and the existing network. Back up workloads and data separately; this module does not provide application backups or disaster recovery.
