# Regional GKE Standard cluster

This root module creates a regional, VPC-native GKE Standard cluster in an existing environment network. It does not create a VPC, subnet, NAT, application identities, Kubernetes policy objects, backups or workload resources. The example `minimal.tfvars` contains placeholders, **not** deployable project or network values.

## Prerequisites

- Enable Kubernetes Engine, Compute Engine, IAM, Cloud Resource Manager, Logging, Monitoring and Artifact Registry APIs in the project. The deploying identity needs permission to create GKE clusters, service accounts and project IAM bindings, use the subnet, and act as the node service account. GKE service agents must be provisioned; organizational policies and quotas must allow the resources.
- `apps-staging` or `apps-prod` must already exist in `project_id`, with regional subnet `<network>-gke-<region>` and secondary IPv4 ranges `pods` and `services`. The ranges must have sufficient free capacity for this cluster, other users, the temporary default pool, the maximum autoscaled pool, and surge upgrades. Each node with 64 max pods normally consumes a /25 pod range. Coordinate range sizing and avoid overlaps.
- Provide a unique, unused RFC1918 /28 for the control-plane peering; it must not overlap subnet, secondary, peered or on-premises networks. The module validates format, not uniqueness or connectivity.
- Nodes have no external IPs. Enable Private Google Access on the subnet for Google APIs and arrange Cloud NAT or equivalent egress for external registries and destinations. Configure DNS, routes and firewall rules including GKE control-plane/node and required application connectivity. NAT and network changes are owned by the network team.
- `master_authorized_networks` must include the actual egress IPs/CIDRs used by cluster administrators, CI, and other API clients. The default public control-plane endpoint is restricted to these ranges; use narrow trusted ranges. For a private-only endpoint set `private_endpoint = true` and provide private routed connectivity from clients; global control-plane access is disabled. Authorized-network enforcement on the private endpoint is not enabled by this module. Check GKE's private endpoint and firewall requirements when planning access.

## Use and operation

Copy `minimal.tfvars` to a private environment-specific tfvars file, replace every placeholder, then run `tofu init`, `tofu plan -var-file=YOUR.tfvars`, and `tofu apply -var-file=YOUR.tfvars`. Authenticate via the environment. Use remote encrypted state with locking and restrict access; state contains cluster connection information and infrastructure details. Get credentials using `gcloud container clusters get-credentials NAME --region REGION --project PROJECT` (use `--internal-ip` with a private endpoint) from an authorized location. Grant operators appropriate GKE IAM and Kubernetes RBAC separately; network access alone does not grant Kubernetes access.

The REGULAR release channel and node auto-upgrade/repair keep the cluster maintained. The daily maintenance window defaults to 09:00 UTC; emergencies and some maintenance can occur outside it. The regional pool defaults to one node minimum and three maximum **per zone** across GKE's default three zones, with one surge node per zone during upgrades. Reserve quota and IP space for surge and for the temporary default pool. Pod disruption budgets, multiple replicas and topology spreading are application responsibilities; a regional cluster alone does not guarantee workload availability. Review versions, maintenance, resource usage, alerts and costs regularly. Set alerts, log retention and a tested workload/volume backup and recovery strategy separately.

Deletion protection defaults to true. To intentionally delete the cluster, first set `deletion_protection = false` and apply, then run destroy. Other destructive changes should also be reviewed in the plan. Protect the state and the deployment pipeline from unauthorized access.

## Isolation and cloud access

Nodes use a dedicated service account with GKE node, logging, monitoring and project Artifact Registry reader roles. The broad cloud-platform OAuth scope is bounded by IAM; do not grant application permissions to this node account. Artifact Registry reader applies project-wide; for stricter repository isolation replace that binding with repository-level grants. Workload Identity Federation for GKE is enabled: create distinct Kubernetes service accounts per workload and grant only the required permissions on the specific Pub/Sub topics/subscriptions, buckets or Cloud SQL resources. Use the Kubernetes service account's Workload Identity principal (or link it to a narrowly scoped IAM service account); configure Cloud SQL connectivity and network access separately. Avoid long-lived service account keys.

Calico network policy enforcement is enabled, but no default-deny policies are installed. Teams must create and test ingress/egress policies, namespace/RBAC boundaries and admission controls appropriate to their workloads. Nodes use Shielded VMs, secure boot, integrity monitoring, container-optimized images and the GKE metadata server. System/workload logs, system metrics and managed Prometheus are enabled; workload logs can contain sensitive data, so configure access and retention accordingly.
