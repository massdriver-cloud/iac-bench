# Application blob storage

This root configuration creates a Standard StorageV2 account in an **existing** application resource group, one private Blob container, and a container-scoped Storage Blob Data Contributor assignment for the application's existing Entra identity. Use one deployment and separate state per application/environment. This is object storage for uploads, media and reports, not an Azure Files share or a filesystem mount.

## Quick start

1. Install OpenTofu >= 1.6 and authenticate the AzureRM provider using your normal environment credentials; set `ARM_SUBSCRIPTION_ID` for the target subscription. The deployment identity needs permission to create/manage storage accounts and blob containers in the resource group and role assignments at the container scope (for example, appropriate Contributor and Role Based Access Control Administrator permissions). The resource group and application service principal/managed identity must already exist in that subscription/tenant.
2. Copy `minimal.tfvars` to your own tfvars file and replace **all** values. The example identity is a placeholder, not a real application. Supply the identity's Entra **object/principal ID**, not its application/client ID. The storage account name must be globally unique across Azure. Choose the resource group's region.
3. Run `tofu init`, `tofu plan -var-file=your.tfvars`, and `tofu apply -var-file=your.tfvars`. Configure a remote, access-controlled state backend and protect state: the provider may store account keys in state even though key authorization is disabled. Role assignment propagation may take several minutes.
4. Pass the `blob_endpoint` and `container_name` outputs to your application. Use an Azure Blob SDK with Entra token authentication (for example, Azure Identity's DefaultAzureCredential). Configure AKS workload identity/federation or enable and select the appropriate App Service managed identity independently; the principal ID supplied here must be the identity the application actually uses. Container-scoped access permits blob operations in that container, not account-wide container enumeration or administration.

## Defaults and operations

The default public Blob endpoint is reachable over the internet, but anonymous access and shared-key authorization are disabled; requests must use Entra authorization. HTTPS and TLS 1.2 or later are required. Encryption at rest uses Azure-managed keys. The account is LRS by default, which does **not** protect against a regional disaster; choose a supported `replication_type` such as ZRS or GRS where the workload requires it and check regional availability and recovery objectives. Blob versioning and 30-day blob and container soft delete help recover accidental changes/deletions, but are not an independent backup, do not prevent storage account deletion, and incur storage charges. Versions do not automatically expire; establish a lifecycle/backup policy appropriate to the application. Shared-key connection strings and account/service SAS are not supported. Direct browser anonymous access is not provided.

For network isolation, set `private_endpoint` to an object containing `subnet_id` and `private_dns_zone_id`. The subnet and the existing `privatelink.blob.core.windows.net` private DNS zone must be in the target Azure cloud, and the deployment identity needs access to both. This creates a Blob private endpoint and DNS zone group and disables public access to the entire account. Link the zone to all client VNets, provide routing and DNS resolution for AKS and App Service (including VNet integration), and allow private endpoint traffic separately. Use the normal `blob_endpoint` hostname, not the private IP. This creates no private endpoints for Azure Files, queues or tables. Private connectivity and DNS are not provisioned for the deployment runner; storage container operations here use the Azure Resource Manager API.

Optional inputs: `container_name` (default `app`), `replication_type` (default `LRS`), `tags`, and `private_endpoint`. Outputs contain the account ID/name, Blob endpoint, container name and optional private endpoint ID. Destroying this root deletes the storage account and its data; use change controls and backups as appropriate.
