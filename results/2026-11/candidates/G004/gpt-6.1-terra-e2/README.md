# Aurora PostgreSQL global database

This root module creates an encrypted Aurora PostgreSQL 16 global database, with two provisioned instances in separate AZs in each of two regions. The secondary is a warm, asynchronously replicated regional cluster, not an independent writable database. Both regional cluster endpoints and ARNs are outputs. The primary writer endpoint is initially the write endpoint; the secondary cluster endpoint becomes writable after promotion. Reader endpoints are also provided.

## Prerequisites and deployment

* In each region there must be exactly one VPC with the `Name` tag `apps-staging` or `apps-prod`, as selected by `environment`, and at least two `tier=database` subnets spanning two AZs. Subnets must be private, with DNS and routing suitable for EKS. Subnet privacy is owned by the network team and is not verified here.
* Supply `name`, `environment`, and the EKS workload security-group IDs in `primary_client_security_group_ids` and `secondary_client_security_group_ids`. The IDs must belong to their respective VPCs. The secure default is **no inbound access**, including in `minimal.tfvars`; configure both lists before deploying a service. Avoid broad shared EKS node security groups where workload-specific security groups are available. Port 5432 is the only allowed inbound port.
* Set `secondary_alarm_actions` to a regional SNS topic ARN wired to an on-call system. Without an action the lag alarm is visible in CloudWatch but does not notify anyone. Monitor availability, capacity, backups and the application separately. Confirm the chosen engine version and instance class support Aurora global databases in both regions; change the default version as needed within PostgreSQL major version 16. Plan upgrades and maintenance explicitly; minor auto-upgrades are disabled to avoid unsynchronized changes.
* Initialize with AWS credentials from the environment, then `tofu plan -var-file=minimal.tfvars`. Use your own production tfvars and a secured, encrypted remote state backend with locking. Apply with sufficient RDS, EC2, KMS, Secrets Manager and CloudWatch permissions in both regions. Four provisioned instances incur continuous cost.

The bootstrap `dbadmin` credential is generated and stored in Secrets Manager with a replica in the secondary region. Global databases cannot rely on RDS-managed master password integration. **The password is also in OpenTofu state and plan files**; encrypt and strictly restrict access to them. Secret replication is asynchronous; verify the replica is in sync before relying on it for recovery. No automatic password rotation is configured. Do not rotate the secret independently of the database: coordinate credential rotation and state management as an operational procedure. Applications should use separate least-privilege database roles, not `dbadmin`.

IAM database authentication is enabled, but applications need database users granted `rds_iam` and workload IAM roles with scoped `rds-db:connect` permissions for the appropriate regional cluster resource IDs (outputs). These users and policies are not provisioned here. Use TLS with certificate and hostname verification (`sslmode=verify-full`) and an up-to-date RDS CA bundle. `rds.force_ssl` is enabled in both regional parameter groups. Ensure application clients reconnect and refresh IAM tokens after failover.

## Recovery operations

Global replication is asynchronous. The two-second lag alarm uses 60-second periods and is an early warning, **not a guarantee of a few seconds of data loss**. During disruption lag can exceed the target or telemetry can be unavailable. Region failover is not automatic, and RTO depends on detection, promotion, routing, client reconnects and AWS availability. Test recovery regularly and measure actual RPO/RTO. Deploy the service, IAM permissions, secrets access, and network connectivity in the DR region ahead of time.

1. Identify and fence the failed writer/application traffic; assess the latest lag and potential loss. Coordinate a single incident owner. During a true outage, run the AWS managed global failover from a working regional control plane: `aws rds failover-global-cluster --region <secondary-region> --global-cluster-identifier <global-id> --target-db-cluster-identifier <secondary-cluster-arn> --allow-data-loss`. This can lose unreplicated writes. For a healthy planned move, use `switchover-global-cluster` instead, without `--allow-data-loss`.
2. Poll `aws rds describe-global-clusters --region <secondary-region> --global-cluster-identifier <global-id>` until the target is writer and available. Redirect the service to the promoted regional writer endpoint, recycle connections, and verify read/write transactions. The module does not configure traffic routing; applications/operations must perform this step.
3. Do not blindly apply this configuration after a role reversal: its primary/secondary resources describe the original topology. Reconcile actual global membership, credentials and IaC state, restore or rebuild the other region, restore alerting, and rehearse a managed switchover back once healthy. Follow AWS's current global database recovery procedure.

Backups are retained for 35 days, logs for 90 days, and deletion protection is enabled. Destruction requires intentionally disabling deletion protection on both regional clusters and the global cluster; final snapshots are requested. Preserve KMS keys for as long as backups or snapshots need them. Backups do not replace cross-region failover testing or restore testing.
