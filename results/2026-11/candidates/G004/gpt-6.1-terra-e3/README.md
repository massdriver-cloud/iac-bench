# Aurora PostgreSQL global database

This root deploys a provisioned Aurora PostgreSQL 16 global database: two instances in distinct AZs in each of two US regions, with an initially writable primary and a warm read-only secondary. Global storage replication is asynchronous. Backups are retained for 35 days; storage and snapshots use the regional AWS-managed RDS KMS keys; PostgreSQL log exports have 90-day retention; instances are private and TLS is enforced. Cluster and global deletion protection are enabled. PostgreSQL minor upgrades are intentionally not automatic; schedule and test coordinated global upgrades and select a version supported in both regions.

## Prerequisites and deployment

* In each region exactly one VPC must have `Name=apps-staging` or `Name=apps-prod`, as appropriate. Its private database subnets must have `tier=database` and span at least two AZs. The network team must ensure private routing, sufficient IP addresses and DNS support. Only clients with the specified regional security groups can connect on TCP 5432; ensure EKS pod/node security groups actually match and allow outbound traffic. The two EKS installations and their traffic failover are outside this root.
* Supply an existing SNS topic in the secondary region with a working on-call subscription and CloudWatch publishing permission. The lag alarm treats missing data as breaching, and is a warning, not a replication guarantee. Set independent availability and application-level alarms too.
* `minimal.tfvars` is an illustrative plan fixture, **not production configuration**: replace its dummy SG IDs, topic, and password. Use a unique high-entropy password from a secure deployment system, e.g. `TF_VAR_master_password`; do not commit it. Use an encrypted, access-restricted, locked remote state backend and restrict saved plans: the password and Secrets Manager secret value are present in state even though marked sensitive. The module copies this credential to a Secrets Manager secret replicated into the second region using AWS-managed Secrets Manager keys. Restrict IAM access in both regions. It does not automatically rotate credentials; plan and test a coordinated database/secret rotation and verify replication before relying on it. AWS credentials and permissions for both regions (including Secrets Manager replication) come from the environment.
* Run `tofu init`, then `tofu plan -var-file=YOUR.tfvars` and `tofu apply -var-file=YOUR.tfvars`. Version and instance class must be available for Aurora Global Database in both chosen regions. VPC lookup requires unique names. This root creates billable resources in both regions.

## Application access

IAM database authentication is enabled in both clusters, but this does not create PostgreSQL application users or grant AWS permissions. Bootstrap least-privilege PostgreSQL roles and grants, grant `rds_iam` to IAM-authenticated users, and attach `rds-db:connect` permissions to the EKS workload roles for **both** regional cluster resource IDs (see `cluster_resource_ids` output). Generate fresh, region-correct IAM tokens for the active endpoint and reconnect before token expiry. Use TLS certificate verification (`sslmode=verify-full`) with the AWS RDS CA bundle, DNS refresh and connection-pool retry/reconnect. Test global writer endpoint and token behavior in both regions with the application's actual drivers. Avoid using the admin user in applications. IAM authentication does not replace PostgreSQL authorization.

## Recovery and operations

Aurora does **not** automatically promote a different region on regional failure. Cross-region lag can exceed seconds, and promotion can lose unreplicated writes; neither RPO nor recovery time is guaranteed. Alert on lag and availability, provision and test EKS capacity in both regions, and regularly exercise failover, restore and the entire application path against the business objectives. Keep an incident operator and authorization available outside the primary region.

For an outage: fence old writers and stop traffic to the old primary; inspect secondary replication lag and assess potential data loss. In the secondary region use the RDS managed global database failover operation targeting the `secondary_cluster_arn` (for example, `aws rds failover-global-cluster --region <secondary-region> --global-cluster-identifier <global_cluster_id> --target-db-cluster-identifier <secondary_cluster_arn> --allow-data-loss`). Wait for promotion, DNS propagation and the global writer endpoint to resolve to the new writer. Switch application traffic to the secondary EKS deployment, reconnect with the new regional IAM tokens and verify writes and business transactions. A planned switchover uses the RDS switchover operation instead and requires healthy replication. The replica secret is available locally; if necessary locate it by name in the secondary region. Never allow independent writable primaries.

Failover changes roles outside OpenTofu: **do not run apply during or immediately after failover**. Reconcile regional roles, resource configuration, alarm placement, secrets ownership and state with the actual AWS topology before any apply; rebuild/rejoin the old region when healthy and test a controlled switchover if returning to the original topology. Replication is not a backup: periodically test point-in-time recovery and snapshots. Destruction requires deliberately disabling global and cluster deletion protection first; final snapshot names are fixed and must not already exist. Recovery and changes require appropriate AWS permissions and operational approval.
