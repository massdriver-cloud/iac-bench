# Aurora PostgreSQL for two-region services

This root module creates one Aurora Global Database per service and environment in a single AWS account. The initial writer region and the recovery region each have two private, provisioned Aurora PostgreSQL instances in different AZs. The recovery region is already running at the same capacity; promotion doesn't wait for instance provisioning or snapshot restore. There is one writable region at a time. Budget for four instances, regional database storage and I/O, replication, backups, and monitoring.

**Recovery objective:** restore application writes within minutes, with a target of no more than 3 seconds of lost commits. Aurora Global Database replicates asynchronously. Managed planned switchovers synchronize before changing writers, but unplanned failovers can lose any commits not replicated to the target. Neither a 3-second alarm nor the Aurora PostgreSQL managed RPO parameter (minimum 20 seconds, with possible commit stalls) provides a hard 3-second guarantee. This module leaves that parameter off to avoid blocking checkout when the only secondary is unreachable. If the loss limit is a hard contractual bound, get a different durability design approved before going live. Measure recovery under load; a successful infrastructure plan does not establish an RTO or RPO.

## Deploy

Use separate, access-controlled, locked state for each service/environment, reachable from the recovery region. Run `tofu init` and `tofu plan -var-file=minimal.tfvars`; apply an approved plan using a file with your real service values. `minimal.tfvars` is a literal checkout example, including example SG IDs and IAM role names. The providers use the environment credential chain. Use OpenTofu 1.11 or later and the locked AWS provider. The deployment role needs the regional RDS, EC2 discovery/SG, KMS, Secrets Manager, CloudWatch, and SNS permissions and permission to attach the scoped managed policy to the designated existing workload roles. Do not grant these provisioning permissions to the application.

Before applying:

- Each selected region must have exactly one VPC tagged `Name=apps-prod` (or `Name=apps-staging`). Each VPC needs private subnets tagged `tier=database` in at least two RDS-capable AZs, with available IPs. The module uses up to three AZs in name order and places the two instances in the first two. Review AZ-set changes in the plan for instance replacements. Keep VPC DNS resolution and the required NACLs/egress in place.
- Pass the security groups actually used by the service's EKS network interfaces in each local VPC (prefer pod SGs). Only those groups get TCP 5432 ingress. DB instances have no public access. The design expects write traffic to be served by EKS **in the writer's region**; it does not create inter-region VPC networking or change service routing. Both EKS stacks, their IAM associations, and their dependencies must be ready for the traffic shift.
- Pass the existing IAM role names used by the service in the two EKS clusters. The module grants `rds-db:connect` for one PostgreSQL login on the two member cluster resource IDs, not AWS administrative permissions or access to the admin secret. The default Aurora PostgreSQL 16 version and `db.r7g.large` class can be overridden. Verify that the version and class are available for Global Database in both regions, and load-test each region for peak traffic. If connections churn, use connection pooling.
- Supply existing same-region SNS pager topics or subscribe your on-call integration to the two output topics and test delivery. Existing topics must allow RDS and CloudWatch to publish (including the required permissions on any SNS encryption key). A 3,000 ms `AuroraGlobalDBRPOLag` alarm is installed in each region; the metric normally exists only on the current secondary. Missing data does not page from the lag alarm. Add an independent, externally paged application write canary in the writer region and monitor secondary reachability and freshness of lag telemetry from outside the writer region. Do not rely on notifications from a region that has failed.

## Bootstrap and connect

The module keeps the admin password in a KMS-encrypted Secrets Manager secret with a replica in the recovery region. It uses ephemeral values and write-only resource attributes, so cleartext is not in the inputs, outputs, plans, or state. Only approved database administrators and the deployment/rotation principals should be able to retrieve it. While both regions are healthy, rotate the password against the **current writer** and update the source secret's `AWSCURRENT` in a coordinated, tested rotation process. Confirm replica sync and test login; the module seeds the credential but does not schedule rotations. Do not change the write-only bootstrap version to rotate. If the original Secrets Manager region is down, use the local replica for retrieval; do not assume it is independently writable.

From an approved private admin client, use the secret and the `admin_username` output to bootstrap the application database. The defaults are shown below; substitute the configured names. Grant only the schema/table/sequence privileges needed at runtime. Use a separate owner/migration role.

```sql
CREATE ROLE app_runtime LOGIN;
GRANT rds_iam TO app_runtime;
GRANT CONNECT ON DATABASE app TO app_runtime;
```

Connect with the EKS IAM role, a fresh RDS auth token for each new physical connection, the RDS CA bundle, and `sslmode=verify-full`. Use `global_writer_endpoint` for write discovery and sign the token for the **current writer region**. During drills verify the client's support for IAM auth and TLS on the AWS global hostname; the regional writer endpoint from `regional_clusters` and its matching signing region are the explicit fallback. Use the same native AWS hostname to generate the token and connect; don't sign against a custom DNS alias. Drain/reopen stale pools on a writer change, honor DNS TTLs, and bound connect/retry time. A lost connection can mean a commit's outcome is unknown; use idempotency keys and reconciliation rather than blindly retrying a payment. The secondary's reader endpoint is suitable only for workloads that accept stale reads.

Regional rotating KMS keys encrypt the data and backups, TLS is required in both clusters, and PostgreSQL logs are retained for 90 days. Database Insights standard mode is enabled. Restrict access to state, snapshots, performance data, and logs; errors and SQL diagnostics can still contain sensitive data. Do not store raw card data when a payment token suffices. The module configures 35-day automated backups; rehearse a point-in-time restore to an isolated network, validate the restored data, and implement separate immutable backups if the retention or account-compromise policy requires them. Replication is not a backup against logical corruption.

## Regional recovery runbook

1. **Prepare before launch.** Have a 24/7 incident role and pager usable from outside the writer region. Grant the role the narrowly scoped RDS permissions for `DescribeGlobalClusters`, `DescribeDBClusters`, `FailoverGlobalCluster`, and `SwitchoverGlobalCluster`, plus the relevant traffic controls. Practice planned switchovers in both directions with the RDS console and the actual application, and rehearse unplanned failover in staging. Drill DNS, token signing, connection pools, throughput, traffic shifts, alerts, and data reconciliation. Record time from first failed write to lastingly restored writes and compare timestamped acknowledged test writes against the newly promoted writer. Have an incident owner authorized to make the data-loss tradeoff without a lengthy approval chain.
2. **Qualify the incident.** A single instance or AZ failure should use Aurora's regional failover, not global promotion. For a writer region outage, keep writes from being routed to the old region, verify the recovery cluster and EKS stack from the surviving region, and note the latest lag and its timestamp. Missing or stale lag is unknown data loss, not zero. If both regions are healthy and this is planned, use managed **Switchover** instead of **Failover**. Do not promote automatically from a lag or connectivity alarm alone.
3. **Promote for an unplanned outage.** Use managed Aurora Global Database failover from the surviving region, without detaching the secondary. With `TARGET_REGION`, `TARGET_CLUSTER_ARN` (from `regional_clusters`), and `GLOBAL_ID` (from `global_cluster_identifier`) set for the incident:

   ```sh
   aws rds failover-global-cluster --region "$TARGET_REGION" \
     --global-cluster-identifier "$GLOBAL_ID" \
     --target-db-cluster-identifier "$TARGET_CLUSTER_ARN" --allow-data-loss
   ```

4. **Restore traffic.** Confirm the target is the global writer using RDS, and run a TLS-verified IAM-authenticated write/read probe from the surviving EKS stack. Update the IAM signing region and endpoint configuration as needed, recycle connections, and shift service traffic to that stack. Check write success, latency, and transaction reconciliation. Record the actual RTO and estimated/measured data loss.
5. **Restore redundancy.** Verify that the original region rejoins as a healthy secondary and catches up before considering a planned switchover back. If it does not rejoin, follow the AWS managed recovery procedure and reconcile state with the actual global membership before another apply. Do not run OpenTofu to initiate promotion, swap `regions.primary` and `regions.secondary`, or assume a successful failover requires reversing the variables. They identify the bootstrap topology and stable resource addresses. Review a refreshed plan after recovery and investigate any proposed changes to topology before applying.

Keep engine versions aligned for managed switchovers and failovers. Change the pinned minor only in a coordinated global upgrade window, then verify the actual version on both members and repeat the drill. Cluster and global deletion protection, final snapshot settings, and OpenTofu destroy guards require deliberate changes for decommissioning. Preserve the KMS keys for as long as retained snapshots or secrets need them.
