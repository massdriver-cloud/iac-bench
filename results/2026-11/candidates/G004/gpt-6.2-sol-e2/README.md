# Aurora PostgreSQL for EKS

Deploy this standalone root once per service and environment, with separate state per deployment. It creates an encrypted Aurora PostgreSQL Global Database, a regional writer cluster with a local failover instance, and a hot secondary cluster. Each region has two provisioned instances in distinct Availability Zones. The standby has the same instance size as the primary and doesn't accept forwarded writes. Defaults are `us-east-1` and `us-west-2`.

## Deploy

1. Use OpenTofu 1.11+ and configure a secured, encrypted, locked remote state backend for your deployment before initializing. Use AWS credentials from the environment for a single account in both regions; do not put credentials in tfvars. Commit the provider lock file generated by `tofu init` for the deployment.
2. Copy `minimal.tfvars` for your service. Replace the example EKS SG IDs and SNS ARNs with real ones. In each region, there must be exactly one VPC with `Name=apps-prod` or `Name=apps-staging` as selected, and private subnets tagged `tier=database` in at least two standard AZs. The module trusts those tags for subnet privacy; the network team owns routing, DNS resolution and NACLs. Check Aurora Global Database engine/class availability, service quotas and subnet capacity in both regions before applying. Review planned instance changes if the tagged AZ inventory changes.
3. Supply the security groups seen as sources from the EKS pods or nodes, depending on your CNI configuration. The module opens TCP 5432 only to those IDs, plus optional explicit private source CIDRs. It does not create VPCs or cross-region routing. If both EKS regions need to reach the writer at the same time, arrange private inter-region routing and DNS and supply the narrow source ranges each DB will actually see. Otherwise, fail over service traffic to the EKS region colocated with the new writer.
4. Supply existing regional standard SNS topics with confirmed on-call delivery and policies allowing their regional RDS event subscriptions and CloudWatch alarms to publish (including KMS permissions if those topics are encrypted). Test notifications in both regions. Also page on application write health from the surviving region or an independent location; RDS events and minute-resolution lag telemetry alone do not detect every outage quickly enough.
5. Set `eks_iam_role_names` to your existing workload roles, or attach `workload_connect_policy_arn` separately. The policy is limited to `rds-db:connect` as one PostgreSQL role on the two cluster resource IDs. It grants neither AWS database administration nor access to the admin secret. Configure the application's service account for EKS Pod Identity or IRSA outside this module.

```sh
tofu init
tofu plan -var-file=service.tfvars
tofu apply -var-file=service.tfvars
```

## Bootstrap and client connections

- The generated break-glass password is passed via ephemeral/write-only values, not stored in OpenTofu state. An authorized bootstrap job or DBA in the private network can retrieve `bootstrap_admin_secret_name` from Secrets Manager; the secret is encrypted under a regional KMS key and replicated to the standby region under its own key. Limit `GetSecretValue` and `kms:Decrypt` to provisioning and audited admin roles. Never give the application this secret. This module seeds the secret; it does not configure automatic rotation. Use a tested admin rotation procedure that changes the password on the current writer, updates `AWSCURRENT`, and verifies the replica. Do not increase either write-only version counter to rotate the password.
- On the current writer, in the database shown by `database_name`, use the admin connection once to create the role from `application_database_user`. For `checkout`, run `CREATE ROLE app_checkout LOGIN;` and `GRANT rds_iam TO app_checkout;`. Then grant `CONNECT` to the database and only the schema and object privileges the service needs. Use a separate migration/ownership role. SQL roles and grants replicate with the database; verify this on the standby and test the EKS IAM login. No SQL provisioning is run by OpenTofu.
- TLS is mandatory. Use the AWS RDS CA bundle and `sslmode=verify-full` (or your driver's equivalent). For IAM authentication, discover the current writer member and use its **regional cluster endpoint** and region for both `generate-db-auth-token` (or the SDK equivalent) and the connection. Do not sign a token for a custom alias or the global writer name. Generate a fresh token for new connections, especially after failover; tokens expire after 15 minutes and are only needed when establishing a connection. The `global_writer_endpoint` output is the AWS-managed name that tracks the writer, but it does not by itself reconfigure IAM token generation, existing connections, or application traffic. Publish the writer region and regional endpoint to your service's runtime configuration through your failover process. Do not pin an instance address, IP, or stale DNS answer.
- Set bounded connection and query timeouts. Recycle pools on writer changes and retry safely. Use idempotency keys and reconcile ambiguous commits rather than blindly replaying checkout or payment writes. Make the standby EKS deployment, its AWS/IAM dependencies, CA trust and traffic cutover part of the recovery drill.

## Regional recovery

**Target: recovery in minutes with only a few seconds of lost writes. This is not a hard guarantee.** Aurora Global Database replicates asynchronously. The standby alarm pages at three seconds of recovery-point lag or if telemetry goes missing. The PostgreSQL `rds.global_db_rpo` setting pauses primary commits at Aurora's supported minimum of 20 seconds if no secondary meets that threshold. This protects against large lag at the cost of write availability; it is **not** a three-second data-loss cap. A sudden outage can leave lag unknown, and failover requires an incident decision. If the business requires a hard few-second upper bound in every failure scenario, Aurora Global Database alone does not meet that requirement.

Keep the global identifier and both regional cluster ARNs, endpoints and on-call permissions accessible outside either region. Use an operator role with tightly scoped RDS failover/switchover and describe access. Do not use OpenTofu as the failover mechanism.

1. Confirm the incident using independent service probes and RDS health. From the healthy region, check the current global membership (`aws rds describe-global-clusters`), the target's health, and the last available `AuroraGlobalDBRPOLag`. Avoid a second promotion while a transition is in progress. Fence traffic to the old writer where possible. The incident lead must explicitly accept possible data loss if the writer is unreachable or lag cannot be verified.
2. For an unplanned regional outage, run the managed failover from the healthy target region. For a planned drill or failback with both members healthy, instead run `switchover-global-cluster` with the same region and identifiers and **without** `--allow-data-loss`. Managed switchover synchronizes the clusters before switching roles.

   ```sh
   aws rds failover-global-cluster --region "$TARGET_REGION" \
     --global-cluster-identifier "$GLOBAL_ID" \
     --target-db-cluster-identifier "$TARGET_CLUSTER_ARN" --allow-data-loss
   ```

3. Verify the target member is the writer (`GlobalClusterMembers[].IsWriter`) and accepts writes from the surviving EKS deployment. Update writer endpoint/region configuration, renew tokens, recycle connection pools and shift service traffic. Check successful application writes and reconcile uncertain transactions. If managed failover isn't available, escalate to the database incident owner rather than independently detaching and promoting replicas.
4. Verify the former primary has rejoined as a healthy secondary and that replication and alerting work in the reverse direction. When both regions and state are reachable, set `monitoring_writer` to the new writer's **original** label, review a fresh plan, then apply the alarm changes. Never swap the configured regions or member identifiers to reflect a failover. Do not apply a plan that proposes replacing a member or changing membership unexpectedly.
5. Rehearse failover and failback before go-live and after material application or engine changes. Measure RTO from loss of successful writes to sustained success from the recovery site, and RPO by comparing acknowledged, timestamped canary writes with the promoted database. A planned switch tests routing and IAM, but does not prove outage RPO; run a staging incident exercise as well.

## Steady-state care

The two member clusters have 35-day automated backup retention, deletion protection and final snapshots. Global deletion protection is also enabled. Verify backup health and periodically test point-in-time restore into an isolated cluster. Replication isn't a backup against accidental data changes. Protect regional KMS keys for as long as their retained backups and logs must remain readable. Review database access and audit requirements separately; neither the module nor the log settings establish payment compliance.

PostgreSQL logs go to KMS-encrypted CloudWatch log groups with 90-day retention, and Performance Insights is enabled. Statement logging is not enabled by default; keep application errors and SQL from including payment or customer data. Provisioned capacity and the engine minor version can be configured. Plan engine upgrades as a coordinated Aurora Global Database change; keep both members on compatible versions for managed recovery and do not treat an engine version edit as routine unattended maintenance.
