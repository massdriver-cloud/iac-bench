# Service database

Deploy once per service/environment, in its own locked, encrypted state. This is **one database with one writable region**, not two independent masters. Aurora Global Database continuously replicates storage to a live secondary with the same capacity as the primary. Each cluster has two provisioned instances in distinct AZs; regional recovery does not depend on provisioning an instance or restoring a snapshot. Size both regions against peak write load before launch.

## Provision and connect

1. Use OpenTofu 1.11+ and credentials for one AWS account. Each region needs a VPC named (tag `Name`) `apps-prod` or `apps-staging`, with `tier=database` private subnets in at least two AZs. Supply the actual security group attached to the EKS workload in each VPC, a workload role name, and a subscribed SNS on-call topic in the recovery region. Only the local group's PostgreSQL traffic is admitted. Coordinate EKS routing, egress, DNS and traffic steering with the network team. Normally run the writing service in the writer region; the other region is ready to take traffic after promotion.
2. `tofu init` and `tofu plan -var-file=minimal.tfvars` exercise the example. For deployment, replace the example identifiers and **omit the example password** from your own tfvars. Inject `TF_VAR_bootstrap_password` from your secret store for plan and apply. Use a strong RDS-compatible password. The write-only input isn't persisted in state; retain it in the break-glass store and increment `password_version` to rotate it. Never grant the app access to this secret. Check chosen engine minor/class availability in both regions and schedule coordinated upgrades.
3. From a trusted private client, connect to the new database as `clusteradmin` over TLS. Once on the writer, execute `CREATE ROLE app_user LOGIN; GRANT rds_iam TO app_user;`. Grant only required schema usage, table, sequence and future-object privileges for this service, using a separate schema owner/migration identity. These catalog changes replicate; IAM permissions by themselves don't create a PostgreSQL login.
4. Configure the EKS service account to assume the supplied role. Use an AWS SDK/driver token provider for each new physical connection as `app_user`; generate the token for the actual regional RDS hostname, port 5432 and its region. Verify the server with `sslmode=verify-full` and the AWS RDS CA bundle. Do not cache expired tokens or use an arbitrary DNS alias for signing. Both regional cluster endpoints are output (labels denote *initial* roles). The global writer DNS output tracks the active writer; for regional IAM token signing use the active region's cluster endpoint directly. Connection pools must discard failed sockets and retry with bounded backoff. Load-test with IAM authentication enabled.

## Regional incident runbook

* Monitor service-level write probes from outside the primary region as well as the secondary's RPO lag alarm. Lag above 3,000 ms, or absent telemetry, pages the SNS topic; check delivery before launch. The alarm is **not** a promotion trigger. Replication is asynchronous: a few seconds RPO and minutes RTO are operating targets, not hard upper bounds. Lag can grow under load or a network partition. A strict worst-case write-loss guarantee requires a different, synchronous commit design with corresponding latency/availability costs.
* Keep a pre-authorized responder and the standby EKS deployment available. Confirm a regional failure rather than a client/network problem, fence writes to the old region, inspect the latest available lag, and get incident-lead approval for possible loss of unreplicated commits. From the **healthy region**, use RDS managed global database failover, targeting its cluster ARN, e.g. `aws rds failover-global-cluster --region "$DR_REGION" --global-cluster-identifier "$GLOBAL_ID" --target-db-cluster-identifier "$DR_CLUSTER_ARN" --allow-data-loss`. Do not delete the primary, detach clusters, or run a Tofu apply to promote.
* Wait for the target to be reported as writer. Switch service traffic to the healthy EKS region, recycle connections using its regional endpoint and fresh tokens, and verify a committed read/write transaction. Reconcile ambiguous payments with idempotency keys/ledger records before retrying. Include detection, approval and client reconnection when measuring recovery time.
* After recovery confirm the old region rejoins as a synchronized secondary; rebuild via the RDS recovery procedure if needed. Reconcile monitoring and IaC with actual roles before any apply. Use a **managed switchover** when both regions are healthy for planned return or drills; don't swap provider regions in state. Rehearse regularly in staging and record elapsed time and last replicated transaction. Roll out only after the end-to-end drill meets the service objectives.

## Data lifecycle

Encryption uses separate rotating customer-managed KMS keys per region. Protect key administration: disabling/deleting a key can render its cluster and backups unusable. Test point-in-time restore separately from failover (replication also copies accidental deletes). Backup retention is 35 days; PostgreSQL logs are exported for 90 days. Restrict access to logs and avoid logging payment details. These controls do not by themselves establish PCI compliance. Before an approved decommission, preserve keys for all retained snapshots, verify a restore, arrange unique final snapshot names, and deliberately disable deletion protection. Do not blindly destroy the stack and its keys.
