# Production Aurora PostgreSQL (two-Region)

This root module creates an **Aurora PostgreSQL Global Database**, not merely a cross-Region snapshot copy. The primary cluster has at least two instances. A secondary cluster in another US Region already has compute running and receives physical storage replication from the primary. Managed Aurora switchover/failover therefore avoids restoring a backup during a Regional outage.

## What the module standardizes

- Two encrypted regional clusters in one Aurora global cluster; two instances per Region by default.
- Existing VPCs and private subnets. By default the module discovers available subnets tagged `tier = database`; explicit subnet IDs are also accepted.
- No public instances and no open ingress. Only the supplied application security groups/CIDRs can reach PostgreSQL.
- KMS encryption with rotation in each Region, RDS-managed master credentials in Secrets Manager, TLS required by `rds.force_ssl`, and IAM database authentication.
- A single `rds-db:connect` policy covering both regional cluster resource IDs, optionally attached to existing EKS service-role names.
- 35-day automated backups, tagged snapshots, deletion protection, final snapshots, minor-version upgrades, and maintenance outside the backup window.
- The same security/logging parameter baseline in both Regions, PostgreSQL log export with one-year retention, Performance Insights, and 60-second enhanced monitoring.
- CPU, memory, and Aurora global RPO-lag alarms. Supply Regional alarm action ARNs to route them to the platform alerting system.

Aurora Global Database is designed for cross-Region replication with a typical RPO of about one second and managed recovery in minutes; these are not unconditional guarantees. Replication lag, failure detection, promotion, application endpoint changes, connection-pool expiry, and application readiness all affect actual RPO/RTO. Run planned switchover drills and measure the complete service recovery.

## Minimal use

Replace the example VPC and subnet IDs in `minimal.tfvars` with real values, or remove both `*_db_subnet_ids` assignments to use tag discovery:

```hcl
name             = "checkout"
database_name    = "checkout"
primary_vpc_id   = "vpc-..."
secondary_vpc_id = "vpc-..."
```

```shell
tofu init
tofu plan -var-file=minimal.tfvars
tofu apply -var-file=minimal.tfvars
```

The default Regions are `us-east-1` and `us-west-2`. Both provider configurations must authenticate to the same AWS account. The chosen engine version and instance class must be available for Aurora Global Database in both Regions.

For an application, normally also set:

```hcl
primary_allowed_security_group_ids   = ["sg-primary-eks"]
secondary_allowed_security_group_ids = ["sg-secondary-eks"]
service_iam_role_names               = ["checkout-primary-eks", "checkout-secondary-eks"]
iam_database_users                   = ["checkout_app"]
primary_alarm_action_arns            = ["arn:aws:sns:us-east-1:...:database-alerts"]
secondary_alarm_action_arns          = ["arn:aws:sns:us-west-2:...:database-alerts"]
```

At least two database subnets in different Availability Zones are required in each Region. Tag discovery is exactly `tier = database`; the network team remains responsible for their private routing. The secondary application security groups and IAM roles must be ready **before** an outage.

## Application and IAM setup

The administrative password is generated by RDS and is not an OpenTofu output. Retrieve it from `master_user_secret_arn` only for bootstrap/break-glass administration. On the primary writer, create each application user listed in `iam_database_users` and grant the IAM authentication role, for example:

```sql
CREATE USER checkout_app WITH LOGIN;
GRANT rds_iam TO checkout_app;
-- Grant only the schemas/tables and privileges this service needs.
```

Database users and grants replicate to the secondary. The generated IAM policy covers the different `dbuser` resource IDs in both Regions. Configure the EKS service account/pod identity to use its IAM role, generate an RDS authentication token for the appropriate regional hostname, and connect with TLS verification (`sslmode=verify-full`). Do not use the master user for normal application traffic.

Before promotion, the secondary reader endpoint is available for disaster-recovery validation. After promotion, applications in that Region must use the **secondary cluster endpoint**, exposed as `secondary_writer_endpoint_after_promotion`. The module deliberately does not publish a public record or silently change application DNS; platform ingress/DNS and connection pools are part of the service recovery runbook.

## Regional recovery runbook

1. Confirm the scope of the outage and the current global-cluster roles. Check the RPO-lag alarm and `aws rds describe-global-clusters`.
2. For a planned event or recovery drill, run the `planned_switchover_command` output. Switchover synchronizes and has no data loss.
3. For a genuine primary-Region failure, run the `regional_recovery_command` output. Managed failover promotes the already-running secondary. `--allow-data-loss` acknowledges that writes not yet replicated can be lost; never use it for a routine switchover.
4. Point recovery-Region applications at `secondary_writer_endpoint_after_promotion`, refresh DNS/connection pools as required, and verify writes, IAM authentication, replication topology, and alarms.
5. Preserve the old Region for diagnosis. Use AWS's managed global-cluster operations to return to a healthy topology rather than deleting clusters manually.

The command outputs describe the **initial** primary/secondary topology. After roles have reversed, choose the current healthy secondary as `--target-db-cluster-identifier`; do not blindly run the old output for failback. OpenTofu resource names remain `primary` and `secondary` for state stability, but Aurora's runtime writer role can differ. A normal plan/apply does not perform a switchback.

## Changes and destruction

Major-version upgrades are intentionally not automatic. Test a new supported `engine_version` against a restored copy, review Aurora global upgrade documentation, and perform a controlled change. `apply_immediately` is false so disruptive modifications use the maintenance window where AWS supports it.

Production defaults set deletion protection and final snapshots. To deliberately destroy, first set `deletion_protection = false` and apply, then destroy while `skip_final_snapshot` remains false. Final snapshot identifiers must be unique in each Region. Protect snapshots, KMS keys, and the managed secret according to the organization's retention policy; destroying encryption keys can make backups unrecoverable.

No registry or remote modules are used.
