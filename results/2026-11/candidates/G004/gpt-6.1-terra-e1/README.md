# Aurora PostgreSQL global database

This root configuration creates a provisioned Aurora PostgreSQL 16 global database, with two private instances in separate AZs in each of two regions. The primary has a local failover reader; the secondary has warm capacity for regional recovery. Storage and replicated admin secret use separate regional KMS keys. Backups are retained for 35 days; deletion protection is enabled; PostgreSQL logs go to CloudWatch for 90 days. IAM database authentication and TLS are enabled, with `rds.force_ssl=1`. The database is not public. Charges are incurred in both regions.

## Prerequisites and use

* Use a single AWS account with credentials authorized in both regions. Check that Aurora global databases, the selected engine version and instance class are supported in both regions and in the selected AZs, and that RDS quotas permit two instances per region. The default is Aurora PostgreSQL 16.6; select a currently available **16.x** global-compatible version where necessary. The parameter groups are for PostgreSQL 16; a major upgrade needs coordinated changes, not just an engine_version change.
* Each region must have exactly one VPC with `Name=apps-staging` or `Name=apps-prod`, and private subnets tagged `tier=database` across at least two AZs. The module does not validate subnet routes or network ACLs: the network team must ensure they are private and allow connections from EKS. Provide EKS source security groups in the corresponding VPC and region, and regional SNS topics with working subscriptions. The IDs and ARNs in minimal.tfvars are illustrative placeholders, not usable infrastructure.
* Configure an encrypted, access-controlled remote OpenTofu backend with locking before applying. Generated credentials are marked sensitive but are stored in state and plans. Restrict access to state, the regional KMS keys and the secret. Secrets Manager stores and replicates the generated admin password; rotation is not automated, and changing the secret alone does not change the database password. Establish and test a coordinated rotation procedure. Services should use separate least-privilege database roles, not the administrator.
* Copy minimal.tfvars and supply actual values, then run `tofu init`, `tofu plan -var-file=...`, and `tofu apply -var-file=...`. The two regions are configured directly on the root providers. Client IAM auth still requires provisioning PostgreSQL users with `rds_iam` and EKS role policies granting `rds-db:connect` for the correct regional DB resource ID and user. Configure clients to verify the RDS CA and hostname, refresh IAM tokens and reconnect on errors. Do not use a custom CNAME for IAM token signing or TLS hostname verification without addressing the RDS endpoint requirements.

## Recovery and limitations

Aurora global replication is asynchronous: seconds of lag are typical, not guaranteed. The secondary alarms on a minute of maximum replication lag over 5 seconds or missing metrics, but this cannot prevent a larger loss during a failure. Regional recovery is **not automatic**: a trained operator must detect the incident, authorize data loss, fail over, and redirect traffic. A minutes-level RTO requires a tested incident process, reachable AWS control plane, healthy secondary capacity, EKS capacity and routing in the secondary region, and clients that reconnect to its writer endpoint. Neither RTO nor RPO is guaranteed by this configuration. Monitor and periodically drill both planned switchovers and unplanned failovers, including DNS/client caching and credential access.

For an unplanned outage, stop/fence writes to the old primary if possible, inspect the last replication lag and declare the risk of lost writes. Using credentials with RDS global failover permissions, invoke `aws rds failover-global-cluster --global-cluster-identifier <global-id> --target-db-cluster-identifier <secondary-cluster-arn> --allow-data-loss --region <secondary-region>`. Wait for completion and verify the target is writable. Route services to the promoted cluster's **writer** endpoint, not its reader endpoint; verify TLS, IAM authorization and application health. The output `secondary_cluster_endpoint` is only a writer after promotion. Reconcile lost transactions and re-establish a secondary region as AWS permits. For planned changes use the AWS managed switchover workflow without allowing data loss. After either operation, the logical primary/secondary roles have changed: do not blindly apply this root until topology, state, alarms and configuration have been reconciled. Reverse the lag alarm and validate the new recovery path.

Before destroying, explicitly disable deletion protection on both clusters and the global database in a controlled change. Final snapshots use fixed names and must not already exist; snapshot retention and restore testing are an operational responsibility. KMS key deletion is delayed 30 days; deleting a key makes remaining encrypted backups unreadable. Never destroy a production database as a substitute for a tested recovery procedure.
